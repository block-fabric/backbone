# The bip300301_enforcer's gRPC interface, served by backboned

Sidechain software on eCash talks to a pair: an eCash node (bitcoind of ecash-com/bitcoin) and the
[bip300301_enforcer](https://github.com/LayerTwo-Labs/bip300301_enforcer), through the enforcer's gRPC API
(`cusf.mainchain.v1`, `cusf.crypto.v1`). backboned serves that API itself (`-grpc`), from its own state, so a
sidechain connects to backboned exactly as to the pair: **Backbone is a drop-in for bitcoind + enforcer**.
The JSON-RPC interface is unchanged (our sidechains keep using it; it says more, see "Our sidechains").

Reference: the enforcer at commit `17eb2ce` (branch `2026-09-16-betanet`, the build betanet runs), read in
`~/skydoge/enforcer`. Paths below are of that repository unless they start with `src/`.

```
backboned -chain=ecashbeta                        # gRPC on 127.0.0.1:50051 and [::1]:50051 (default on eCash networks)
thunder --mainchain-grpc-url http://127.0.0.1:50051   # a LayerTwo sidechain, unchanged
grpcurl -plaintext 127.0.0.1:50051 list           # reflection
curl -d '{}' -H 'Content-Type: application/json' http://127.0.0.1:50051/cusf.mainchain.v1.ValidatorService/GetChainTip
```

| Auth, TLS | none | none by default (drop-in); optional token `-grpcauth` for the spending/mining services; see §7 |

| Health | `grpc.health.v1` (connectrpc-health `StaticChecker`, `app/main.rs:774-775`): SERVING for each service served; the Rust sidechains check it first and treat NOT_FOUND as "not served" | the same: `""` and each service served → SERVING, others NOT_FOUND; Watch streams |

| Errors | `ConnectError` codes; field errors INVALID_ARGUMENT with fixed texts (`lib/proto.rs:238-327`); database errors INTERNAL (`internal_err`, `lib/server/mod.rs:28-30`) | the same codes and the same leading texts (§4) |

The `.proto` files: the enforcer's (`proto/cusf/...`) carry **no license** (the repository has no LICENSE file;
`gh api repos/LayerTwo-Labs/bip300301_enforcer` reports none; so does `cusf_sidechain_proto`). They are not
copied: `src/grpc/proto` is our own definition, written from the interface, with the same package, message,
field and method names, numbers, types, labels, oneofs and options. `contrib/devtools/gen-grpc-descriptors.py
--compare <enforcer checkout>` checks that, descriptor by descriptor: identical to 17eb2ce but for two methods
added on purpose (below). The descriptor set embedded (`src/grpc/descriptors.cpp`, regenerated by the same
script) includes Google's `wrappers.proto` and `timestamp.proto` (BSD-3-Clause, shipped with protoc).

## 3. Where the answers come from

- **Headers** (BlockHeaderInfo, `lib/proto.rs:813-823`): hash and parent ReverseHex; `work` is the block's own
  work (`header.work()`, not the chain's), 32 bytes little endian (ConsensusHex of `[u8; 32]`); `timestamp` the
  header time. From the block index (`GetBlockProof`).
- **A block's info for a slot** (`MakeBlockInfo`, `src/grpc/services.cpp`; the enforcer's `connect_block`,
  `lib/validator/task/mod.rs:1089-1287`, and `BlockInfo::only_sidechain`, `lib/types.rs:805-843`):
  - only for a block that was connected (its drivechain record exists), the genesis block, and blocks
    below the activation height (empty, `task/mod.rs:1115-1118`);
  - `bmm_commitment`: the slot's M7 (the BMM index; the block itself if not indexed);
  - events in the enforcer's order: the coinbase's M3 (Submitted, in output order), the bundles that failed
    (in pending order: pending after the parent, not after the block, not paid by it; `handle_failed_m6ids`,
    `task/mod.rs:612-649`), then per transaction in block order deposits (sequence number, treasury outpoint,
    address = the OP_RETURN data, value = what the deposit added) and payouts (Succeeded: sequence number,
    the M6 consensus-serialized);
  - sequence numbers: the escrow changes of the slot before (the enforcer's treasury UTXO count,
    `dbs/mod.rs:110-145`), counted on the block's own chain (also for a stale block).
- **Events**: from the validation interface, after the subscription (queued callbacks are drained first);
  nothing is sent on subscribing (Thunder's, truthcoin's and coinshift's handshake GetChainTip, SubscribeEvents,
  GetChainTip needs that); a reorg is DisconnectBlock for each block taken back, newest first, then ConnectBlock
  in order; a subscriber that lets more than 256 MiB pile up is ended as the enforcer's overflow; never closed
  for being idle.
- **Activation records**: the drivechain database now records, per block that activated a sidechain, its
  proposal's height and acks (`Database::ReadActivation`), which the enforcer keeps in its sidechain status.

## 4. Conventions

- `ConsensusHex`: the consensus serialization as hex: a `[u8; N]` as it is (hashes in internal order:
  `m6id`, `bmm_commitment`, `critical_hash` are the reverse of the RPC's hex), a `Vec<u8>` with its compact size
  first (`description`). `ReverseHex`: reversed (block hashes, txids, as the RPC shows them). `Hex`: as it is.
- Replies are written canonically (field number order, proto3 defaults left out: a 0 in a wrapper is an empty
  wrapper, `{}`), as the enforcer's buffa encoder writes them; requests are read leniently (any order, packed or
  not, unknown fields skipped).
- Errors (INVALID_ARGUMENT): "Missing field in message \`M\`: \`f\`", "Invalid field value in field \`f\` of message
  \`M\`: \`v\`" (then `: cause`, in the words of the Rust crates the enforcer decodes with: the hex crate for `ReverseHex` and `Hex`,
  rust-bitcoin's lazy `deserialize_hex` for `ConsensusHex`; checked against the enforcer, §10). Others as in §2.

## 5. Differences, gaps

- **More data, never less**: header infos also for headers the enforcer never synced (stale branches of the
  node); GetBlockInfo for a stale block the node once connected (the enforcer too keeps those).
- **Activations before this version** have no record: GetSidechains leaves `vote_count` and `proposal_height`
  unset for them (no eCash network has such history with Backbone yet).
- **SubscribeHeaderSyncProgress**: the enforcer reports its own header sync from its node; ours the node's
  header height while in initial block download, ending when it is over.
- **Wallet, block producer**: our wallet and template, so the differences of §2 (fee estimate, locktime,
  outbid, per-sidechain votes, ALL policy); the enforcer's BDK specifics (mnemonics, electrum/esplora sync
  sources: reported as DISABLED) do not exist.
- **Stop** refused unless `-grpcallowstop`; **WalletService** not served on eCash's main network unless
  `-grpcwallet` (§6, §7).
- Not served: Connect's gzip, `grpc-web-text`, gRPC over HTTP/1.1 (gRPC needs HTTP/2), TLS.
- An assumeutxo snapshot node: the escrow index starts at the snapshot (as for the RPC methods).

## 7. Security

The enforcer has no authentication and binds to localhost; its clients send none; so the drop-in default is
the same for the ValidatorService. What is added, from the security review of 2026-10-20:

1. **Web pages** (CSRF, DNS rebinding): a request with an `Origin` header is refused (403 /
   PERMISSION_DENIED) unless its origin is in `-grpcallowedorigin`; a `Host`/`:authority` that is a name other than
   `localhost` (an IP literal is fine) is refused unless in `-grpcallowedhost`; Connect's GET form only for
   methods marked `NO_SIDE_EFFECTS`; POST only with the protocols' content types (no form or text types, which a
   page can send without a preflight).
2. **Bounded buffers**: HTTP/1.1 holds at most one request (16 MiB; a chunk declared bigger closes the
   connection before it is read; 64 KiB while a request is served); HTTP/2: 256 streams, flow control by hand
   (window updates for the bytes taken in), 64 MiB of request bytes per connection and 256 MiB in all (a stream
   over them is reset with ENHANCE_YOUR_CALM), a decoded request's bytes freed at once. Replies are not bounded
   (GetBlockInfo of 1000 blocks; the clients accept 1 GiB).
3. **The token** (`-grpcauth`) for what spends, mines, decides votes or stops the node.
4. **Defaults**: Stop opt-in; WalletService opt-in on eCash's main network; beyond localhost only with an allow
   list and the token.
5. **Slow clients** (slowloris; as the Flush public API's row 10, 2026-10-21, and its review): a request (its
   headers and body) must be all in within 15 s of its first byte however slowly it trickles (over HTTP/2 each
   stream from its own HEADERS), else the connection is closed; a connection with no call running that began or
   completed no request for 30 s is closed, over HTTP/2 with a GOAWAY first (gRPC clients open another; a call
   sent meanwhile is above its last stream id, so retried); bytes alone are not activity (PINGs, SETTINGS); a
   client whose replies wait must take at least 4 KiB a second of them (or all that waited) over each 30 s, else
   it is closed: a byte now and then does not keep it open (slow reads: replies waiting in the socket, in a call
   or behind HTTP/2 flow control all count; a stream whose window stays closed 30 s is reset); above 1 MiB
   waiting for the socket nothing more is taken from the calls (backpressure), and a connection holding more than
   384 MiB of replies in all is closed; a call's unsent replies are at most 320 MiB (then RESOURCE_EXHAUSTED; SubscribeEvents ends its subscriber at 256 MiB
   first, as the enforcer); past 100 streams reset before their call was over, by the client (Rapid Reset, stream
   rotation) or by the server because of the client (MadeYouReset, CVE-2025-8671: oversized or malformed
   frames), each counted once, the connection is closed with a GOAWAY (nghttp2's own reset rate limit too; depends
   builds nghttp2 1.66.0, which has its MadeYouReset fix; an older system libnghttp2 is warned about at startup); past 10,000 requests it takes no new one (GOAWAY) and
   is closed once its calls are over;
   a running call is otherwise never cut (SubscribeEvents and other server streams last as long as their client
   reads them); 16 connections per address beyond this machine, IPv6 counted by its /64 (`-grpcipv6prefix`, 16 to
   128), the loopback addresses (shared by the machine's own sidechain nodes and apps) not bounded by address;
   256 in all.

Tests: `grpc_tests/transport`, `grpc_tests/limits`, `grpc_tests/connection_states`, `grpc_tests/slow_clients`,
`grpc_tests/slow_reads_and_rotation`, `grpc_tests/flow_control_and_rapid_reset`, `grpc_tests/address_keys`; `interface_ecash_grpc.py`
(`test_security`, `test_slow_clients`).

## 8. Why nghttp2 and our own protobuf code

| | grpc++ (gRPC's C++ library) | nghttp2 + our codec (chosen) | all our own (HTTP/2 + HPACK too) |
|---|---|---|---|
| Dependencies | grpc, protobuf, abseil, re2, c-ares, upb, zlib, BoringSSL/OpenSSL | libnghttp2 (MIT, C, no dependency) | none |
| depends + mingw | days of packaging, a moving target (abseil, protobuf ABI) | `depends/packages/nghttp2.mk`, 30 lines, built for x86_64-w64-mingw32 | none |
| Size | +10–15 MB | +~150 KB | +~80 KB |
| Attack surface | large, but well fuzzed | HTTP/2 framing and HPACK in a library fuzzed by OSS-Fuzz (curl, nginx, Apache use it); our code: request routing, the codec | HPACK and flow control written anew: the riskiest part |
| Protocols | gRPC; gRPC-Web and Connect would still be ours | gRPC, gRPC-Web, Connect (all three the enforcer serves) | same |

The codec (`src/grpc/protobuf.cpp`) reads the descriptors protoc writes, so the definitions are in one place
(`src/grpc/proto`) and reflection serves the same descriptors. protoc is needed only to regenerate
`descriptors.cpp`, not to build.

## 11. Our sidechains

They keep JSON-RPC (default): `getsidechainevents` reports the bundles pending after each block with their
scores, which the template's consensus uses (refund gating) and which the enforcer's interface does not have
(only the current votes, GetWithdrawalBundleProposals). The template branch `ecash-grpc` (worktree
`~/skydoge/sidechain-template-ecash-grpc`) adds `-mainchaingrpcport`/`-mainchaingrpcauth`: its BMM requests and
withdrawal bundles go through the enforcer's interface (Connect JSON over its own HTTP/1.1 client; the hand-off
upvoted by the block producer; its word on the bundle, and following, stay on JSON-RPC, since the interface cannot withdraw a word). Its
`doc/mainchain-grpc.md` has what is mapped, the limits, and the design of a full
gRPC mode, which needs the pending scores per block from the enforcer (or a replay of the votes).
`feature_sidechain_ecash.py --mainchaingrpc` runs the whole eCash scenario that way against backboned.
